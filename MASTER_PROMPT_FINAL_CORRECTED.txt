==================================================
QUALITY LOOP BẮT BUỘC — ANTIGRAVITY ↔ OPENAI REVIEW
==================================================

Đây là yêu cầu BẮT BUỘC, không phải gợi ý.

Mục tiêu là tạo vòng lặp chất lượng độc lập:

ANTIGRAVITY IMPLEMENT / FIX
-> BUILD / TEST TRONG DOCKER
-> INDEPENDENT OPENAI CODE REVIEW
-> nếu REJECT: ANTIGRAVITY FIX
-> BUILD / TEST LẠI
-> FRESH OPENAI CODE REVIEW
-> lặp đến APPROVE
-> GEMINI LIVE QA
-> OPENAI FINAL GATE
-> nếu REJECT: quay lại ANTIGRAVITY FIX
-> lặp lại toàn bộ chu kỳ
-> chỉ DONE khi FINAL GATE APPROVE

==================================================
PHÂN VAI AGENT / CATEGORY / MODEL
==================================================

1. IMPLEMENTATION / FIXING

Ưu tiên các implementation agent theo cấu hình Oh My OpenAgent:
- sisyphus
- hephaestus
- atlas
- sisyphus-junior

Ưu tiên Antigravity cho coding, refactor, sửa bug và triển khai.
Nếu model chính hết quota hoặc lỗi provider, cho phép runtime_fallback xử lý theo omo.jsonc.
Không tự dừng chỉ vì một model cụ thể hết quota nếu fallback còn khả dụng.

2. ARCHITECTURE / DEEP REASONING

Ưu tiên:
- oracle
- prometheus
- metis
- category: ultrabrain
- category: deep

Model thực tế được quyết định bởi omo.jsonc và runtime fallback.
Không hard-code giả định rằng một provider cụ thể luôn khả dụng.

3. EXPLORATION / RESEARCH

Ưu tiên:
- librarian
- explore
- category: quick khi phù hợp

Các task đọc repository, tìm file, tổng hợp context và kiểm tra nhanh có thể chạy song song nếu độc lập.

4. INDEPENDENT CODE REVIEW

KHÔNG gọi các agent type không được runtime hỗ trợ như:
- omo-native-code-reviewer
- omo-native-qa-executor
- omo-native-gate-reviewer

BẮT BUỘC delegate review bằng category:

task(category="code-review")

Category `code-review` trong omo.jsonc là nguồn cấu hình model.

Kỳ vọng ưu tiên hiện tại:
- primary: openai/gpt-6-sol, reasoning xhigh
- fallback 1: openai/gpt-5.6-sol, reasoning xhigh
- fallback 2: openai/gpt-5.3-codex-spark, reasoning high
- fallback 3: google/antigravity-claude-opus-4-6-thinking

Reviewer phải độc lập với implementation agent.

Reviewer KHÔNG được:
- tin IMPLEMENTATION_STATUS.md chỉ vì file ghi DONE
- tin README là bằng chứng implementation
- tin REVIEW_FINDINGS.md cũ
- tin QUALITY_GATE.md cũ
- tin báo cáo của implementation agent
- tin kết luận APPROVE từ vòng review trước
- chỉ đọc summary rồi approve
- tự nhận đã chạy test nếu không có evidence thực tế

Reviewer PHẢI:
- tự đọc source code thực tế
- tự đọc Dockerfile và infra/compose.yaml
- tự đọc migration/schema
- tự đọc security/auth/RBAC/access policy
- tự đọc test hiện có
- tự kiểm tra API/backend/frontend quan trọng
- tự xem trạng thái source tree hiện tại
- tự chạy hoặc kiểm chứng command build/test cần thiết
- đối chiếu implementation với tài liệu yêu cầu đính kèm
- kiểm tra IDOR, cross-class, cross-user và privilege escalation
- kiểm tra entitlement, PRO, exam audience và answer leakage
- kiểm tra payment/webhook/idempotency/refund
- kiểm tra media permission/presigned URL
- kiểm tra segment parser/injection
- kiểm tra outbox/projection consistency
- kiểm tra frontend có dùng API thật hay chỉ mock/hard-code
- kiểm tra test có thực sự chứng minh behavior hay chỉ test hình thức
- đưa verdict rõ ràng: APPROVE hoặc REJECT

Nếu REJECT:
- ghi finding cụ thể
- ghi severity
- ghi file/module liên quan
- ghi cách reproduce hoặc evidence khi có
- không tự sửa trong cùng vai reviewer nếu có thể tách vai trò
- chuyển findings về implementation loop

5. LIVE QA EXECUTION

Chỉ chạy QA sau khi Independent Code Review APPROVE.

BẮT BUỘC delegate bằng category:

task(category="qa")

Kỳ vọng ưu tiên hiện tại:
- primary: google/antigravity-gemini-3.8-flash
- fallback: theo omo.jsonc

QA phải kiểm tra hệ thống đang chạy thật qua Docker.
Không được coi việc đọc code hoặc đọc report là QA.

QA phải ưu tiên kiểm tra:
- frontend thực tế
- backend health
- login/authentication
- classroom access
- OWNER / STAFF / STUDENT boundaries
- FREE / PRO / EXPIRED behavior
- learning flow
- exam flow
- store / order / payment mock / entitlement
- Studio permission
- forbidden/expired/error states
- API unauthorized behavior
- các user journey quan trọng từ tài liệu

6. FINAL QUALITY GATE

Sau QA PASS, BẮT BUỘC delegate bằng category:

task(category="final-gate")

Category `final-gate` trong omo.jsonc là nguồn cấu hình model.

Kỳ vọng ưu tiên hiện tại:
- primary: openai/gpt-6-sol, reasoning xhigh
- fallback 1: openai/gpt-5.6-sol, reasoning xhigh
- fallback 2: openai/gpt-5.3-codex-spark, reasoning high
- fallback 3: google/antigravity-claude-opus-4-6-thinking

Final Gate phải độc lập với implementation agent và QA executor.

Final Gate phải đưa đúng một verdict chất lượng:
- APPROVE
hoặc
- REJECT

Không được kết thúc dự án nếu Final Gate chưa APPROVE.

==================================================
QUY TẮC VÒNG LẶP REVIEW
==================================================

Sau MỖI milestone implementation lớn:

1. Antigravity implementation agents triển khai hoặc sửa.
2. Chạy build/test phù hợp trong Docker.
3. Delegate MỘT independent review mới bằng category `code-review`.
4. Reviewer tự kiểm tra source + evidence hiện tại.
5. Nếu REJECT:
   - cập nhật docs/REVIEW_FINDINGS.md
   - biến từng finding thành task sửa cụ thể
   - giao lại cho implementation agents
   - sửa code
   - chạy build/test lại
   - delegate MỘT review `code-review` MỚI
   - review lại trạng thái source/evidence mới
6. Lặp FIX -> TEST -> FRESH REVIEW cho đến khi APPROVE.
7. Sau APPROVE mới delegate category `qa`.
8. QA chạy kiểm tra live trên Docker stack.
9. Nếu QA FAIL:
   - quay lại implementation sửa
   - build/test lại
   - fresh code-review lại
   - QA lại
10. Sau QA PASS mới delegate category `final-gate`.
11. Nếu Final Gate REJECT:
   - quay lại implementation sửa
   - build/test lại
   - fresh code-review lại
   - QA lại
   - final-gate lại
12. Chỉ khi Final Gate APPROVE mới được đánh dấu milestone DONE.

Không được dùng kết luận review cũ để tự xác nhận trạng thái code mới.
Sau mỗi thay đổi do finding sinh ra phải có fresh review trên code mới.

Không được để implementation agent tự review và tự APPROVE code của chính nó.

==================================================
BACKEND DOCKER BUILD
==================================================

Backend phải dùng multi-stage Docker build.

Logic mong muốn:

builder stage
  -> Maven + JDK 21
  -> download dependencies
  -> compile
  -> test nếu phù hợp
  -> package jar

runtime stage
  -> JRE 21
  -> copy jar
  -> chạy application

Không yêu cầu Maven/JDK trên host.

Ưu tiên dependency caching Docker tốt để rebuild nhanh.

Tạo .dockerignore phù hợp.

Backend container phải có:

- health endpoint
- readiness
- graceful shutdown nếu phù hợp

==================================================
MODEL / RUNTIME TRUTH
==================================================

Không được khẳng định một model cụ thể đã review chỉ vì prompt đặt tên model đó.

Chỉ ghi model reviewer/QA/gate là model cụ thể khi:
- runtime log hiển thị model đó, hoặc
- task/subtask metadata xác nhận model đó.

Nếu runtime chỉ hiển thị category/role mà không hiển thị model:
- ghi category/role đã chạy
- ghi model là "UNVERIFIED BY RUNTIME"
- KHÔNG giả mạo rằng GPT-6 Sol, GPT-5.6 Sol, Codex hoặc model khác đã thực sự được gọi.

Nếu category delegate fail:
- ghi lỗi thật
- dùng fallback độc lập nếu có thể
- không đổi tên một General Agent thành "GPT-6/Codex reviewer" nếu không có evidence model.
